# 33. 검증 보강 — 출발지 단위 분할 · 지름길 진단 · 1시간 누적 uniq_objects

> 날짜: 2026-11-12 · 관련: `docs/12`(지도 vs 비지도), `docs/27`(피처셋), `docs/32`(피처 선택 원칙)
> 코드: `ml/supervised.py`(--split), `ml/shortcut_auc.py`(신규), `ml/features.py`(--cum-hours)

## 0. 왜 했나

팀원 파이프라인(team_one `ml/src/…`, 30초 창 RF, 2026-11-02 팀 레포에서 폐기)과 비교하다가 나온 세 가지.

1. 내 `supervised.py` 는 정상 구간을 **시각순 앞/뒤**로 나눴다 → 같은 출발지(IP)가 학습·평가 양쪽에 들어가
   모델이 출발지를 외워 맞힐 수 있다(누수 → 낙관적 수치). 팀원도 첫 노트북(세션 앞 75%/뒤 25%)에서 같은 문제로 과신했다.
2. 팀원이 ML 을 접은 이유 = "피처 하나(`error_404_ratio`)가 정답지 역할을 하는 **지름길**" + "느리게/브라우저처럼 하면 행동 통계로 구분 불가".
   → 내 데이터에도 지름길이 있는지 확인 필요.
3. 내 목표(다른 도구가 못 잡는 이상행위, 그중 **느린 공격**)에 대해 팀원 반박은 **속도·리듬 피처에는 맞고, '무엇을 건드렸나'(범위) 피처에는 안 맞는다**는 가설
   → 범위를 긴 기간 누적으로 보는 피처로 확인.

PoC 단계에서 처음부터 필요한 평가 요소는 ① 출발지 단위 분할 ② 정상 오탐률 ③ 룰 비교군 — ②③은 이미 있었고 ①만 빠져 있었다.

## 1. `supervised.py` — 출발지 단위 분할 (`--split ip`, 기본)

| | `--split ip` (신규 기본) | `--split time` (이전 방식) |
|---|---|---|
| 정상 평가 | 정상 출발지 중 `--normal-test`(0.3) 비율을 **통째로** 뗌 (`--seed`) | 정상 구간 시각순 뒤 30% |
| 공격 학습 | 평가 대상 묶음의 출발지는 그 회차 학습에서 **완전히 제외** (그 IP 의 다른 공격·공격 시간 밖 구간 포함) | 제외 안 함 |
| 공격 출발지의 공격 시간 밖 구간 | 오탐률 평가에서 제외(공격자라서). 다른 회차에선 정상 학습에 사용 | 정상으로 학습·평가 모두 사용 |

- IF·LOF·AE·스케일러도 회차별 정상 학습셋으로 맞춤. 정상 출발지가 2개 미만이면 중단(→ `--split time`).
- **검증 범위:** 문법 통과, sklearn 을 가짜 모듈로 바꿔 끝까지 실행(합성: 정상 출발지 6개 중 2개=11구간 평가, 26구간 학습 확인; real_canon: 14개 중 4개=50구간 평가).
- **미검증:** 실제 모델 수치. 이 PC(Windows)는 애플리케이션 제어 정책이 scipy DLL 을 차단해 sklearn 이 import 되지 않는다
  (`ImportError: DLL load failed while importing _stats: 애플리케이션 제어 정책에서 이 파일을 차단했습니다`).
  → sklearn 이 도는 환경(VM/Docker)에서 `--split ip` vs `--split time` 비교가 다음 할 일.

## 2. 지름길 진단 (`ml/shortcut_auc.py`, numpy 만)

단일 피처 AUC(방향 무관). ≥ 0.99 면 "피처 하나로 다 갈림".

### 합성 `data/features_combined.csv` (정상 37 / 공격 7) — **지름길 있음**

| 피처 | 전체 AUC |
|---|---|
| `err_ratio` | **1.000** ← 정상 37구간 전부 0, 공격 전부 ≥ 0.29 |
| `uniq_objects` | 0.834 |
| `req_count` | 0.824 |

→ 2026-10-23 슬랙 정리의 **"느린 BOLA 는 LOF 만 잡았다 → IF+LOF+RF 근거 확보"는 철회**.
이 데이터에선 `err_ratio` 하나로 전부 갈리므로 LOF 가 행동 패턴을 잡은 건지 `err_ratio` 를 본 건지 구분 불가.
게다가 그 '느린 BOLA'는 분당 6회(5분 창 30회)로 진짜 느린 공격이 아니다.

### 실데이터 정본 `datasets/real_web/real_canon_*` (정상 214 / 공격 32) — 전체 지름길 없음

전체 기준 최고 `err_ratio` 0.779. 종류별로는 갈리는 피처가 있다:

| 종류 | 혼자 거의 완벽히 가르는 피처 |
|---|---|
| bola · bola_fast · bola_slow · user_enum | `uniq_objects` (1.000) |
| brute_slow | `err_ratio`, `write_ratio` (1.000) — `uniq_objects` 는 전부 0 |
| harvest | `req_count`, `max_req_1min`, `interval_cv` (1.000) |

`boost_bola_*` 는 정상 구간이 없어 진단 불가.

## 3. 1시간 누적 `uniq_objects` (`features.py --cum-hours H`)

정의: 구간 끝 시각까지 **직전 H시간** 동안 그 출발지가 건드린 소유 자원 객체의 **합집합** 크기(구간별 수의 합이 아님). 과거만 사용.
옵션을 안 주면 열이 생기지 않아 기존 스키마(`accumulate.py`)는 그대로.

- 회귀 확인: `--cum-hours` 없이 다시 뽑은 real_canon 피처 = 저장된 정본과 동일(줄바꿈 제외), 1h 출력의 기존 9열도 동일.

### real_canon 결과 (원본 `real_canon_access.log.gz` 에서 재추출)

| 출발지 | 5분 `uniq_objects` | 1시간 누적 | 24시간 누적 |
|---|---|---|---|
| 정상 (214구간) | 0~**4** | 0~**6** | 0~**6** |
| bola_slow (6구간) | **4**~20 | **11**~40 | **16**~40 |
| bola | 12~80 | 20~80 | 20~80 |
| bola_fast | 120 | 120 | 120 |
| user_enum | — | 60 | 60 |

- 5분 창에선 느린 BOLA 의 가장 낮은 구간(4)이 정상 최대(4)와 **같다** — 이미 경계에 걸려 있었다(AUC 표기는 1.000 이지만 동점 1건).
- 1시간 누적에선 간격이 **6 → 11** 로 벌어지고, 24시간에선 **6 → 16**. 정상은 누적해도 거의 안 늘고(4→6), 느린 BOLA 는 쌓인다.
  → "속도는 숨겨도 범위는 못 숨긴다"와 맞는 방향.
- AUC 는 이미 1.0 근처라 개선이 안 보인다 — 효과는 **여유(margin)** 로 봐야 한다.

### 한계 (이 결과로 주장할 수 없는 것)

- 느린 BOLA 는 **출발지 1개·6구간**뿐. 일반 성질인지 이 사건 하나의 성질인지 모른다.
- 정상 214구간 중 198구간이 `uniq_objects` 0 — 실제 쇼핑객은 자기 장바구니·주문을 보므로 이렇게 0이 많지 않을 것.
  정상 트래픽이 소유 자원을 거의 안 건드리게 만들어졌다면 간격 일부는 **데이터 생성 방식의 흔적**일 수 있다.
- 정상 출발지 대부분이 06:20~17:50 로 길지만 일부(107~112)는 30분뿐 — 누적 피처는 관측 기간이 짧은 출발지에서 작게 나온다.
- 구조적으로 못 잡는 것: 범위가 필요 없는 표적 접근(1건), 여러 IP·계정으로 나눈 공격.
- 실제 모델(IF/LOF/RF)에 넣은 탐지율·오탐률은 아직 없음 (§1 sklearn 차단).
